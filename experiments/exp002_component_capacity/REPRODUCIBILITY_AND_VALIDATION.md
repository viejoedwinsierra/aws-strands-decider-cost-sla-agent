# EXP-002 — Reproducible deployment candidate

## Scope
This package updates EXP-002 only. No AWS deployment or load-test `run` was performed during preparation. EXP-001 is not included or changed.

## Changes
- `prepare_dependencies.sh`: fixes actual newline separators in `requirements.lock` and `experiment.env`; checks lockfile line count; publishes wheels, lockfile and checksum manifest under a SHA-256 versioned S3 prefix.
- `deploy_fastapi.sh`: offline installation from full pinned lockfile; checksum verification before installation; exact installed-version comparison, `pip check`, evidence snapshots, hash-specific virtualenv.
- `deploy_locust.sh`: same versioned-bundle, offline lockfile and verification strategy; hash-specific virtualenv and evidence.
- `verify_locust.sh`: verifies the versioned virtualenv instead of obsolete `venv311` path.
- `scripts/verify_locked_environment.py`: checks every locked distribution against installed package metadata.
- `tests/test_local_reproducibility.py`: offline local tests including *generated* SSM command syntax, semantic lockfile and configuration updates.

## Offline validation
From this directory:

```bash
python3 tests/test_local_reproducibility.py
```

The test uses temporary fake wheel filenames and a temporary experiment.env; it does not call AWS or install dependencies.

## Deployment prerequisites and known limits
- Execute from the full repository where `exp002_component_capacity` lives under `experiments/`.
- A writable AWS profile, region, SSM managed EC2 permissions and S3 permissions are needed. The EC2 instance role must be able to read the versioned S3 bundles.
- `bootstrap_all.sh deploy` provisions resources and can incur AWS charges. Review `create_bucket.sh` and `provision.sh` before running.
- Local checks are **PASS**, but actual EC2 installation, network access, `systemd`, and S3 IAM remain **UNTESTED**.
- The `run` branch in `bootstrap_all.sh` still references EXP-001 patterns. Do not use `run` until separately redesigned.
- This candidate fixes exact-version installation. Full cryptographic supply-chain assurance additionally requires a trusted initial wheel provenance and immutable S3 storage; SHA-256 alone does not authenticate the publisher.
- Re-running `pip download` at a later time can resolve newer transitives; keep each published `requirements.lock` and its bundle hash as the experimental version identifier.
- The uploaded ZIP did not include `config/experiment.env`; that runtime file must be present or generated by provisioning. No runtime identifiers or credentials are bundled.

## Deploy acceptance criteria
1. Bundle publication succeeds and `FASTAPI_BUNDLE_HASH`, `LOCUST_BUNDLE_HASH` are saved as separate lines in config.
2. Both SSM installs succeed with lock verification PASS and `pip check` PASS.
3. PostgreSQL and FastAPI systemd services are active; `/health` returns expected JSON.
4. Locust executable works from its hash-specific venv.
5. Security group rules are restricted to Locust -> workload TCP/8001, and private connectivity succeeds.
6. Archive execution logs and actual dependency evidence before marking deployment validated.

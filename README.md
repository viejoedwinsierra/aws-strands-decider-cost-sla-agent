# AWS Cost & SLA Decision Agent

An experimental, evidence-driven approach to AWS infrastructure decisions using **Strands Decider 2B**, performance measurements, and deterministic decision guardrails.

The project explores how infrastructure recommendations can balance service-level objectives (SLOs), operational risk, and technological costs.

> **Project status:** Prototype under active development for the AWS Agent Experience Hackathon. Local Decider inference and the EXP-001 evidence workflow have been validated. Automated agent orchestration, Amazon Bedrock integration, and AWS agent deployment are not yet implemented.

## 1. Problem

Infrastructure decisions should not rely exclusively on latency, throughput, or error rates. A service may satisfy its performance thresholds while lacking sufficient evidence to justify scaling or cost optimization.

This project separates:

- **Observed evidence:** Measurements collected from infrastructure experiments.
- **Experimental SLA evaluation:** Deterministic checks against configured thresholds.
- **Model recommendation:** An operational choice generated by Strands Decider 2B.
- **Policy validation:** A guardrail that limits recommendations when critical evidence is missing.

The goal is not simply to minimize infrastructure costs, but to support explainable decisions that consider performance, cost, and operational risk.

## 4. Strands Decider 2B

The project uses the model:

`StrandsAgents/strands-decider-2B-hobson-v19`

The experimental decision options are `Maintain`, `Optimize`, `Scale Up`, and `Insufficient Evidence`.

### Run the local baseline

Install the optional Decider dependencies:

```bash
python -m pip install -e ".[decider]"
```

The baseline requires an environment compatible with the model and its inference dependencies. CUDA is the default device; local hardware requirements depend on the execution environment.

Run:

```bash
bash examples/decider_baseline.sh
```

To select a device and output path:

```bash
DECIDER_DEVICE=cuda bash examples/decider_baseline.sh /tmp/decider_baseline.json
```

The script generates a JSON response containing the model choice, option probabilities, confidence, and token usage. **This baseline uses a hardcoded experimental state rather than automatically reading the evidence adapter output.**

### Observed baseline result

| Field | Value |
|---|---|
| Model decision | Insufficient Evidence |
| Decision probability | 0.6146 |
| Reported confidence | 0.4861 |

The probability of the selected choice and the reported confidence are distinct output fields.

## 5. Evidence Adapter

The evidence adapter reads `metrics_normalized.json` and `sla_evaluation.json` from a run directory. It checks that both files refer to the same experiment and run, then constructs a state, question, and choice list for Decider.

Example (replace `<run_id>` with an existing local run directory):

```bash
python src/decider/evidence_adapter.py \
  experiments/exp001_capacity/results/<run_id>
```

The adapter prints JSON to standard output. Run evidence is excluded from Git by design; generate your own evidence before using this command.

## 6. Decision Guardrail v0.2

The guardrail consumes a Decider JSON response and a normalized evidence JSON file.

Example (replace `<run_id>` with an existing local run directory):

```bash
python src/decider/decision_guardrail.py \
  /tmp/decider_baseline.json \
  experiments/exp001_capacity/results/<run_id>/metrics_normalized.json
```

The current experimental policy requires these additional measurements:

- `cpu_utilization`
- `memory_utilization`
- `capacity_headroom`
- `infrastructure_cost`

The current implementation looks for these fields under the top-level `additional_metrics` object in the evidence JSON. When any required measurement is missing, the effective decision is constrained to `Insufficient Evidence`.

The output distinguishes:

- `model_decision`: The original model recommendation.
- `effective_decision`: The recommendation after applying policy.
- `guardrail_applied`: Whether missing evidence triggered the policy.
- `decision_overridden`: Whether the policy changed the model choice.
- `missing_evidence`: Required measurements not available.
- `policy_version`: The experimental guardrail version.

### Validated guardrail result

For EXP-001:

```json
{
  "model_decision": "Insufficient Evidence",
  "effective_decision": "Insufficient Evidence",
  "guardrail_applied": true,
  "decision_overridden": false,
  "missing_evidence": [
    "cpu_utilization",
    "memory_utilization",
    "capacity_headroom",
    "infrastructure_cost"
  ],
  "policy_version": "experimental-v0.2"
}
```

This guardrail is an experimental prototype, not a complete production policy engine. It does not independently establish that the model response belongs to the evidence run, nor does it validate the semantics or units of additional measurements.

## 7. Reproducing EXP-001

The experiment automation is located in `experiments/exp001_capacity/infrastructure/`.

Configuration template: `experiments/exp001_capacity/config/experiment.env.example`.

Create a local configuration file and provide the required AWS resource identifiers and settings. The experiment includes automation for infrastructure provisioning, HTTP service setup, load generation, metric normalization, SLA evaluation, and evidence archival.

The scripts were developed in an **AWS Academy sandbox** environment and may depend on lab-managed AWS resources, permissions, and networking. They are not guaranteed to run unchanged in a standard AWS account.

**Important:** Provisioning EC2 instances and storing evidence in Amazon S3 may incur AWS charges. Review scripts, permissions, resource configuration, and cleanup procedures before executing them.

Original local experiment artifacts are excluded from Git by design.
